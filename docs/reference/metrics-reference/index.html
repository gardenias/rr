指标参考 / Metrics Reference

Rr 使用 metrics crate（v0.24）记录指标，由 rr-server 的 Prometheus exporter 暴露。通过 NodeConfig::with_metrics_port(port) 启用后，端点为 http://<host>:<metrics_port>/metrics。

Rr records metrics with the metrics crate (v0.24) and exposes them through rr-server's Prometheus exporter. After NodeConfig::with_metrics_port(port), scrape http://<host>:<metrics_port>/metrics.

启用与验证 / Enable and Verify​

let config = NodeConfig::new(node_id, listen_addr, storage, config_provider, sm_factory)
    .with_metrics_port(62001); // Prometheus HTTP 端口 / Prometheus HTTP port
curl http://127.0.0.1:62001/metrics

Console 实时与历史 / Console Live and History​

Console BFF 抓取上述逐节点 /metrics，将实时序列保存在有界内存中；重启会清空数据，时间窗只筛选已留存数据， 不会回填 Console 启动前的历史。Prometheus 不是实时功能的必需依赖；成对配置 --prometheus-url 与 --prometheus-cluster 后，Console 才可查询固定 raw-family 历史模板，不开放任意 PromQL。详见 Cluster Admin Console › 留存、新鲜度与规模 中的留存语义。

The Console BFF scrapes the per-node /metrics endpoints above and retains live series in bounded memory. Restarting clears this data; time windows only filter retained observations and never backfill history from before Console startup. Prometheus is not required for live data. Pairing --prometheus-url with --prometheus-cluster enables fixed raw-family history templates, not arbitrary PromQL. See Cluster Admin Console › Retention, Freshness, and Scale.

命名惯例 / Naming Conventions​

Rr 当前混用两种命名风格，未来版本会统一 / Rr currently mixes two naming styles; future versions will unify them:

  • rr_ 前缀 + 下划线（Prometheus 推荐）/ rr_ prefix with underscores (recommended by Prometheus):
    rr_proposal_duration_seconds, rr_raft_current_term, rr_channel_reconnects_total

  • 点分隔（legacy）/ Dot-separated legacy names:
    router.route.not_found, node.started, raft.group.start

Prometheus 会把点转换为下划线，例如 router.route.not_found 查询为 router_route_not_found。 为保持稳定的指标契约，新代码应使用 rr_ 前缀。

Prometheus converts dots to underscores, so router.route.not_found is queried as router_route_not_found. New code should use the rr_ prefix for a stable metric contract.

服务端指标 / Server-Side Metrics​

所有指标由 Prometheus exporter 在 scrape 时收集。histogram 以原生 Prometheus histogram（_bucket 序列）导出，可用于 histogram_quantile() 与跨实例聚合；bucket 边界在 rr-server/src/node.rs 的 recorder 安装处配置，*_seconds 共用延迟 bucket 组。

The Prometheus exporter collects all metrics at scrape time. Histograms are exported as native Prometheus histograms (_bucket series) for histogram_quantile() and cross-instance aggregation. Bucket boundaries are configured where the recorder is installed in rr-server/src/node.rs; *_seconds metrics share one latency bucket set.

节点资源 / Node Resources​

节点仅在启用 metrics 端口后启动资源采样器，每 5 秒采样一次。平台或 cgroup 不支持的值不会发射； 缺席不是零。文件系统口径取包含 boot journal 目录的最长前缀挂载点；未配置 journal 目录时使用进程当前目录。

The resource sampler starts only when the metrics port is enabled and samples every five seconds. Values unsupported by the platform or cgroup are omitted, never exported as zero. Filesystem metrics select the longest-prefix mount containing the boot-journal directory, or the process working directory when no journal directory is configured.

写链路延迟证据 / Write-Path Latency Evidence​

以下指标描述不同边界的样本，应并排分析，而不是拼成互斥的延迟预算：

These metrics observe samples at different boundaries. Analyze them side by side, not as a partition of one latency budget:

  • rr_client_request_duration_seconds：SDK 端到端请求，含重试。 / SDK end-to-end requests, including retries.
  • rr_server_request_duration_seconds{op="write"}：dispatch 边界写入。 / Writes at the dispatch boundary.
  • rr_proposal_duration_seconds：client/batch 提案到 commit + apply。 / Client/batch proposals through commit and apply.
  • rr_raft_apply_duration_seconds：每个副本的状态机 apply。 / State-machine apply on every replica.

  • rr_raft_append_entries_rtt_seconds：Leader→follower heartbeat/append RTT。/ Leader-to-follower heartbeat and append RTT.

禁止未对齐样本相减 / Never Subtract Unaligned Cohorts

当前 server histogram 没有 outcome，proposal 还区分 client/batch，apply 又在每个副本逐条记录。 失败、redirect、重试和 batch 会使样本集合不同；相同 group_id、Leader 和时间窗也不能证明对齐。 因此 server、proposal、apply 的均值不得相减或堆叠，分位数也不得相减、相加或堆叠。Console 将此状态标为 UNALIGNED_COHORTS，独立展示各段均值和分位数。

The current server histogram has no outcome; proposal distinguishes client and batch; apply is recorded per entry on every replica. Failures, redirects, retries, and batches select different samples. Matching group_id, leader, and time window does not prove alignment. Never subtract or stack server/proposal/apply means, and never subtract, add, or stack their quantiles. Console reports UNALIGNED_COHORTS and presents each segment independently.

只有未来版本提供对齐的 outcome/cohort 标签，并验证所选 server/proposal/apply 样本计数一致后，才可重新评估 均值构成；分位数仍永远不可做构成减法。

Mean composition may be reconsidered only after a future version supplies aligned outcome/cohort labels and equal selected sample counts are verified across server, proposal, and apply. Quantile composition remains invalid.

尾部分析使用各段自身的 rr:server_request_duration_seconds:p99_1m、rr:proposal_duration_seconds:p99_1m、 rr:apply_duration_seconds:p99_1m 和 rr:append_entries_rtt_seconds:p99_1m。P99 必须先按 le 和所需维度聚合 histogram bucket，再调用 histogram_quantile()；禁止平均节点或副本的 P99。

For tail analysis, use each segment's own rr:server_request_duration_seconds:p99_1m, rr:proposal_duration_seconds:p99_1m, rr:apply_duration_seconds:p99_1m, and rr:append_entries_rtt_seconds:p99_1m. Compute P99 by aggregating histogram buckets by le and the required dimensions before histogram_quantile(); never average per-node or per-replica P99 values.

deploy/observability/prometheus/rr-recording-rules.yml 中预计算的 rr:*:p99_1m recording rules 使用 1m 窗口；直接查询原始 histogram 时可选其他窗口，下方 histogram_quantile() 示例使用 5m。长拖尾窗口会在负载 停止后保留历史最坏样本，并在爬升时混合工况；需要当前工况时优先使用 1m 规则。read 与 lin_read 不经过 Raft 复制，rr_server_request_duration_seconds{op} 的 total 即该 dispatch 边界的全链路。

The precomputed rr:*:p99_1m recording rules in deploy/observability/prometheus/rr-recording-rules.yml use a 1m window. Direct queries against raw histograms may choose other windows; the histogram_quantile() example below uses 5m. Long trailing windows retain historical worst samples after load stops and mix regimes during ramp-up, so prefer the 1m rules for the current regime. read and lin_read skip Raft replication, so the total from rr_server_request_duration_seconds{op} is the full chain at that dispatch boundary.

链路追踪 / Tracing​

原 Phase 3 观测性计划已全部落地：rr_raft_replication_lag 自 v0.2.0 可用；W3C trace context 传播自 v0.2.0 由 rr-network::tracing 的 extract_/attach_traceparent 助手和 examples/otel-client 示例提供。 OpenTelemetry SDK（OTLP exporter）按设计不内置，由用户自带。

The original Phase 3 observability plan has landed: rr_raft_replication_lag is available since v0.2.0, and W3C trace-context propagation shipped in v0.2.0 through rr-network::tracing extract_/attach_traceparent helpers and examples/otel-client. The OpenTelemetry SDK and OTLP exporter are deliberately not bundled; bring your own OTLP stack.

Prometheus 配置 / Prometheus Configuration​

每个 target 必须带稳定且唯一的 node_id，并用精确的集群标签隔离同名 group。不要使用 instance 反推 node ID。Console 历史直接使用原始 histogram/counter/gauge family，并为每次查询强制精确集群 matcher 和节点 映射校验；它不消费 recording rules。供其他查询使用的 recording rules 也应保留集群和节点标签。

Every target needs a stable, unique node_id and an exact cluster label to isolate same-named groups. Never infer node IDs from instance. Console history queries raw histogram/counter/gauge families directly and enforces the exact cluster matcher and node mapping on every query; it does not consume recording rules. Recording rules used by other queries should also preserve cluster and node labels.

scrape_configs:
  - job_name: 'rr-cluster'
    static_configs:
      - targets: ['127.0.0.1:62001']
        labels: {cluster_id: 'prod-rr', node_id: '1'}
      - targets: ['127.0.0.1:62002']
        labels: {cluster_id: 'prod-rr', node_id: '2'}
      - targets: ['127.0.0.1:62003']
        labels: {cluster_id: 'prod-rr', node_id: '3'}
    scrape_interval: 15s

查询示例 / Query Examples​

# 每组每秒提案数 / Proposals per second per group
sum by (group_id) (rate(rr_proposal_duration_seconds_count[1m]))

# p99 提案延迟 / p99 proposal latency
histogram_quantile(0.99, sum by (le, group_id) (rate(rr_proposal_duration_seconds_bucket[5m])))

# 当前全部 Leader / All current leaders
rr_raft_is_leader == 1

# 每秒路由失败 / Routing lookup failures per second
rate(router_route_not_found[1m])

# 连接池抖动 / Connection-pool churn
sum(rate(rr_channel_reconnects_total[5m])) by (node_id)

# 集群写入 TPS（apply 精确口径）/ Cluster write TPS (exact applied entries)
rr:applied_entries_rate_1m

# 按操作类型的请求 TPS / Request TPS by op
rr:server_request_rate_1m:by_op

# Kafka 链路 TPS / Kafka-path TPS
rr:ingestor_commands_rate_1m

# p99 客户端请求延迟（按 op，1m）/ p99 client request latency by op (1m)
rr:server_request_duration_seconds:p99_1m

# p99 Leader→follower AppendEntries RTT
rr:append_entries_rtt_seconds:p99_1m

# 各段均值独立比较；不要相减或堆叠 / Compare segment means independently; never subtract or stack
rr:apply_seconds:mean_1m
rr:proposal_seconds:mean_1m
rr:server_request_seconds:mean_1m{op="write"}
