兼容性与 API 稳定性 / Compatibility & API Stability

本文声明 Rr 的版本兼容承诺，用于选择版本和规划升级。

This document states Rr's compatibility commitments for choosing versions and planning upgrades.

版本号方案 / Versioning Scheme​

Rr 遵循 Semantic Versioning 2.0.0：MAJOR.MINOR.PATCH。

Rr follows Semantic Versioning 2.0.0: MAJOR.MINOR.PATCH.

版本位 / Component何时递增 / When it bumps
MAJORpublic Rust API、gRPC wire、磁盘格式或 config schema 的破坏性变更 / Breaking changes to public Rust APIs, gRPC wire, on-disk formats, or config schema
MINOR向后兼容的功能、API、gRPC 方法或可选 config 字段 / Backward-compatible features, APIs, gRPC methods, or optional config fields
PATCH向后兼容的缺陷与安全修复 / Backward-compatible bug and security fixes

Pre-1.0 语义 / Pre-1.0 Semantics​

1.0.0 前采用 Cargo 惯例：0.x.y 中 x 递增可包含破坏性变更。因此 0.2.0 → 0.3.0 可破坏 API，0.2.0 → 0.2.1 不可。

Before 1.0.0, Rr follows Cargo convention: incrementing x in 0.x.y may break APIs. Thus 0.2.0 → 0.3.0 may break APIs, while 0.2.0 → 0.2.1 may not.

兼容性层次 / Compatibility Tiers​

1. Rust 公共 API / Rust Public API​

同一 MAJOR 内，docs.rs 可见的 pub 项保持源码兼容；cargo update 到同 MAJOR 的新版本后应无需 修改代码即可编译。

Within one MAJOR, every pub item visible on docs.rs remains source-compatible; cargo update within that MAJOR should not require code changes.

以下不在承诺内 / Explicit non-commitments:

  • 标记为 #[doc(hidden)] 的 API。

    APIs marked #[doc(hidden)].

  • 模块路径含 __ 或 internal 的 API。

    APIs whose module path contains __ or internal.

  • 外部 trait 的 impl，因为 upstream 可添加默认方法。

    Implementations of external traits, because upstream may add default methods.

  • MSRV 提升属于 MINOR，而非 MAJOR。

    MSRV increases are MINOR, not MAJOR, changes.

2. gRPC Wire Protocol​

同一 MAJOR 内，已发布 .proto 字段保持 wire 兼容，新旧 client/server 可互通。新增字段必须向后兼容 （新的 optional 或 repeated），已分配字段号永不重用。

Within one MAJOR, published .proto fields remain wire-compatible so old and new clients and servers interoperate. New fields must be backward-compatible (optional or repeated), and assigned field numbers are never reused.

混合版本集群 / Mixed-version clusters:

  • patch 混合（如 0.2.0 + 0.2.1）：支持，推荐滚动升级。

    Patch-level mixing (for example 0.2.0 + 0.2.1) is supported and rolling upgrades are recommended.

  • pre-1.0 minor 混合（如 0.2.x + 0.3.x）：不支持，请一次性升级整个集群。

    Pre-1.0 minor mixing (for example 0.2.x + 0.3.x) is not supported; upgrade the whole cluster together.

  • 1.0 起：遵循标准 MAJOR/MINOR/PATCH 语义；具体 minor 混合支持范围记录在 CHANGELOG。

    Starting at 1.0, standard MAJOR/MINOR/PATCH semantics apply; the supported scope of minor-version mixing is stated explicitly in the CHANGELOG.

3. 磁盘格式 / On-Disk Format (RocksDB Schema)​

patch 升级（0.2.0 → 0.2.1）可直接滚动重启，无需迁移。

Patch upgrades (0.2.0 → 0.2.1) support direct rolling restarts without migration.

Raft 日志 payload 对存储层是不透明字节，apply 侧按 magic 前缀解释：\0rrENT01 = FramedEntry， \0rrBAT01 = client 批处理帧（apply 时拆分），无 magic = 原始应用字节（v0.2.x 语义）。

Raft log payloads are opaque to storage and interpreted by magic prefix at apply: \0rrENT01 means FramedEntry, \0rrBAT01 means a client batch frame split during apply, and no magic means raw application bytes (v0.2.x semantics).

批处理回滚 / Batching rollback

批处理开启期间产生的 \0rrBAT01 条目会被旧二进制作为单条不透明 payload 交给 service。回滚前 必须关闭 client 批处理并滚动重启。

Older binaries hand \0rrBAT01 entries written while batching was enabled to the service as one opaque payload. Disable client batching and perform a rolling restart before downgrading.

跨 MAJOR 或 pre-1.0 MINOR 可能需要先 rr-admin backup → shutdown → clean data_dir → upgrade → restore，或使用专门迁移工具。具体步骤会在该版本 CHANGELOG 说明。

Across MAJOR or pre-1.0 MINOR boundaries, migration may require rr-admin backup → shutdown → clean data_dir → upgrade → restore, or a dedicated migration tool. The release CHANGELOG states the procedure.

4. Config File Schema​

同一 MAJOR 内，已有 TOML 键的含义与默认值不变；新键始终 optional，默认值保持旧行为。重命名或删除键 需要 MAJOR bump。

Within one MAJOR, existing TOML keys retain their meaning and defaults. New keys are optional and default to the old behavior. Renaming or removing a key requires a MAJOR bump.

rr-server 使用 #[serde(deny_unknown_fields)] 拒绝未知键，使拼写错误 fail-fast，而非静默降级。

rr-server uses #[serde(deny_unknown_fields)] to reject unknown keys, so typos fail fast instead of silently degrading behavior.

5. CLI Flags & Env Vars​

CLI 标志和 RR_* 环境变量在同一 MAJOR 内只做添加型变更；改名或删除需要 MAJOR。变更记录在 CHANGELOG 的 Changed / Deprecated / Removed。

CLI flags and RR_* environment variables are additive within one MAJOR; renaming or removal requires a MAJOR bump. Changes appear under Changed / Deprecated / Removed in the CHANGELOG.

6. Console HTTP API 与启动兼容 / Console HTTP API and Startup Compatibility​

rr-admin console 现在允许无 peers/discovery 的独立启动；旧启动参数创建一个进程内临时连接并保留原有无作用域 资源路由。该固定映射不会切换到其他连接，无临时连接时旧数据面返回 400 CONNECTION_REQUIRED。新客户端应使用 /api/v1/console/connections 控制面和 /api/v1/console/connections/{id}/... 数据面。连接 mutation 与 reconcile 都使用同源 Origin 和 session CSRF；控制面 meta 的 cluster_id 为 null。

rr-admin console now starts independently without peers/discovery. Existing startup arguments create one in-memory ephemeral connection and retain the legacy unscoped resources. This fixed mapping never switches to another connection; without it, legacy data routes return 400 CONNECTION_REQUIRED. New clients use /api/v1/console/connections for control and /api/v1/console/connections/{id}/... for data. Connection mutations and reconcile require same-origin Origin and session CSRF; control-plane meta has a null cluster_id.

完整机器契约是 crates/rr-admin/openapi/console-v1.json。console.v1 响应 schema 保留既有能力降级和分页语义； 连接控制错误使用明确 4xx/5xx code，秘密字段 write-only。浏览器当前连接由 URL query 决定，不是后端全局状态。 本地 connections.json 另有显式格式版本和原子 0600 写入，损坏/未来版本不会按空 store 打开。升级时无需迁移 Raft 数据，但部署需为 --state-dir 或默认平台配置目录提供持久、独占且可写的存储。

The machine contract is crates/rr-admin/openapi/console-v1.json. The console.v1 response schema retains capability degradation and pagination semantics; connection control errors have explicit 4xx/5xx codes and secrets are write-only. The browser's selected connection is URL state, not a backend global. Local connections.json has a separate explicit format version with atomic mode-0600 writes; corrupt or future versions never open as an empty store. Upgrading requires no Raft data migration, but deployments must provide persistent, exclusive, writable storage for --state-dir or the platform configuration default.

7. Metrics​

同一 MAJOR 内，已发布 metric 名称和标签稳定；删除或重命名需要 MAJOR，新增 metric 或 label 属于 MINOR。

Published metric names and labels are stable within one MAJOR. Deleting or renaming one requires a MAJOR bump; adding a metric or label is a MINOR change.

字节格式版本约定 / Byte-Format Versioning Policy​

自 2026-09-23 起，任何新引入的协议层或持久化字节格式必须携带类型魔数前缀和显式版本位。解码端必须 拒绝 version > 当前支持版本，不得猜测未知布局。版本位仅在非兼容演进时递增；同版本内只允许新增 可选尾部字段。crates/rr-core/tests/golden/ 金色语料与畸形/未来版本拒绝测试用于锁定格式。

Since 2026-09-23, every new protocol-layer or persisted byte format must carry a type magic prefix and an explicit version field. Decoders must reject version > supported rather than guess an unknown layout. Bump the version only for incompatible evolution; within one version, only optional trailer fields may be added. The golden corpus in crates/rr-core/tests/golden/ and malformed/future-version rejection tests pin these formats.

同版本可选尾部字段支持老 reader/新 writer（老节点忽略尾部），新 reader 读到老 writer 的缺失字段时按 None 处理。新字段的生产者只能在全集群部署可解码新版本的二进制后开启：先全量部署，再逐台打开写入 开关。无法执行两阶段滚动时必须递增版本位，让老节点响亮拒解。

Optional trailer fields within one version support old readers with new writers, which ignore the trailer; a new reader sees an absent old-writer field as None. Enable a producer of a new field only after every node runs a binary that can decode it: deploy first, then enable writes node by node. If this two-phase rollout is impossible, bump the version so old nodes reject the format loudly.

2026-09-23 格式升级未保留 legacy 兼容代码。正式 v0.2.0 不生成这些 sidecar；只有其后的 interim builds 可能 带有旧裸文件。interim sm-snapshot.bin 会 fail-closed 启动失败，sm-membership.bin 会 warn 后从空启动并重建。 这类部署需要按实际 commit 制定恢复手册，不要把通用恢复步骤当作正式 v0.2.0 的迁移流程。

The 2026-09-23 format upgrade intentionally retained no legacy compatibility code. Released v0.2.0 does not create these sidecars; only later interim builds may contain legacy raw files. An interim sm-snapshot.bin fails closed at startup, while sm-membership.bin is skipped with a warning and rebuilt. Such deployments require a runbook for their actual commit; these generic recovery notes are not a released-v0.2.0 migration procedure.

最低支持 Rust 版本 / Minimum Supported Rust Version (MSRV)​

当前为 Rust 1.98（workspace Cargo.toml 的 rust-version）。

The current MSRV is Rust 1.98, set by rust-version in the workspace Cargo.toml.

  • MSRV 提升属于 MINOR，并记录在 CHANGELOG Changed。

    MSRV bumps are MINOR changes recorded under CHANGELOG Changed.

  • PATCH 不提升 MSRV。

    PATCH releases never raise MSRV.

  • 目标为 stable - 6 months，为下游预留升级时间。

    The target is stable - 6 months, giving downstream users time to upgrade.

弃用流程 / Deprecation Process​

  1. 宣布：添加 #[deprecated(since="x.y.z", note="use Foo instead")]，并记录在 CHANGELOG Deprecated。

    Announce: Add the attribute and record it under CHANGELOG Deprecated.

  2. 宽限期：至少保留一个完整 MINOR 周期，期间功能仍可用并可能发出警告。

    Grace period: Keep the API functional for at least one full MINOR cycle, possibly with warnings.

  3. 删除：在下一个 MAJOR 删除，并记录在 CHANGELOG Removed。

    Remove: Remove it in the next MAJOR and record it under CHANGELOG Removed.

pre-1.0 下“下一个 MAJOR”指下一个破坏性 MINOR。例如 v0.2.0 弃用的 DurabilityPolicy::Balanced/Fast 已在实际发布 v1.0.0 时删除（跳过了原计划的 v0.3.0 版本号）。

Under pre-1.0 semantics, “next MAJOR” meant the next breaking MINOR. For example, DurabilityPolicy::Balanced/Fast were deprecated in v0.2.0 and removed in the actual v1.0.0 release, skipping the originally planned v0.3.0 version number.

支持政策 / Support Policy​

版本线 / Branch接收内容 / Receives
Latest MAJOR新功能、bug 与安全修复 / Features, bug fixes, and security fixes
Previous MAJOR仅 N-1，6 个月安全与严重 bug 修复 / N-1 only: security and critical bug fixes for 6 months
Older不受支持，需升级 / Unsupported; upgrade required

检查升级兼容性 / Checking Upgrade Compatibility​

按顺序检查 / Check in this order:

  1. CHANGELOG.md：破坏性变更列在 ## [x.y.z] 下的 ### Changed、### Removed 或 ### Breaking。

    Breaking changes appear under ### Changed, ### Removed, or ### Breaking below ## [x.y.z].

  2. 所用 crate 的 docs.rs diff：检查消失的公共 API。

    The docs.rs diff for your crate shows removed public APIs.

  3. 本地 cargo check：通过通常表示源码兼容；失败应由前两项解释。

    Your own cargo check verifies source compatibility; failures should be explained by the first two.

报告兼容性 Bug / Reporting Compatibility Bugs​

PATCH 升级后 cargo check 失败或 wire mix 失败，请提交 bug，附最小复现、升级前后版本、实际与预期行为。

If cargo check or wire interoperability fails after a PATCH upgrade, report a bug with a minimal reproducer, before/after versions, and actual versus expected behavior.

邮件：gardenia.wu@outlook.com（或提交 GitHub issue）。

Email: gardenia.wu@outlook.com (or open a GitHub issue).
