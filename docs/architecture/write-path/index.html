完整写入链路 / Complete Write Path

从 send_request() 到客户端响应，写入依次跨越进程、Tokio task、Raft、业务和存储边界。

From send_request() to the client response, a write crosses process, Tokio task, Raft, business-logic, and storage boundaries.

关键边界 / Key Boundaries​

进程边界 / Process Boundary​

图中是三个独立 OS 进程，仅通过 TCP gRPC 通信。进程崩溃不会直接破坏其他进程的内存，但该组失去多数派时仍无法提交写入。

The diagram shows three independent OS processes communicating only over TCP gRPC. A crash does not directly damage another process's memory, but the group still cannot commit writes after losing quorum.

Raft 边界 / Raft Boundary​

RaftCore 和 SM Worker 由 openraft 驱动；IoBatcher 是 rr-raft 的日志存储组件。应用业务代码不能注入这些协议路径。

Openraft drives RaftCore and the SM Worker; IoBatcher belongs to rr-raft's log storage. Application business code cannot inject logic into these protocol paths.

保证 / Guarantee条件与含义 / Condition and Meaning
持久性 / DurabilityStrict 下，client_write() 返回 Ok 前，条目已在多数派完成日志持久化。
Under Strict, client_write() returns Ok only after the entry's log persistence completes on a majority.
顺序性 / Ordering各节点按相同 log index 顺序 apply。
Every node applies entries in the same log-index order.
Leader 唯一性 / Leader uniqueness同一 term 只有一个 leader 接受写入。
Only one leader accepts writes within a term.

业务边界 / Business Boundary​

Service::handle(payload) 是业务逻辑入口。

Service::handle(payload) is the business-logic entry point.

  • SM Worker 会等待其完成；不要执行阻塞 IO，以免阻塞 apply pipeline。
    The SM Worker awaits it; do not perform blocking IO and stall the apply pipeline.
  • 接收者是 &self；内部可变状态需要自行同步，例如 Arc<RwLock<HashMap>>。
    The receiver is &self; synchronize interior mutable state, for example with Arc<RwLock<HashMap>>.
  • leader 和 follower 都按相同顺序执行，因此实现必须确定。
    Leaders and followers execute it in the same order, so implementations must be deterministic.

Memory-cached; rocks mode atomically writes tmp → fsync → rename for InstallSnapshot and restart recovery, while mem mode is memory-only.
