# v0.2 → v0.3 Migration Guide

:::info Release status
v0.3.0 is currently **in development on `main`** and has not been tagged. This guide describes how to upgrade an existing v0.2.x deployment once v0.3.0 is cut; until then, the new features are only available when building from `main`.
:::

> **Target audience**: operators of existing rr v0.2.x clusters preparing to upgrade.
> **Effort**: ~1 hour for a code-only upgrade; ~4 hours if you adopt Kafka input or idempotency.

v0.3.0 is a **forward-compatible**, **rolling-upgradable** release. v0.2.x snapshots are auto-migrated on first read; the wire-level Raft RPC format is unchanged. New features (idempotency, Kafka input) are opt-in — code that worked under v0.2.x compiles and runs under v0.3.0 with one exception (see [Breaking changes](#breaking-changes) below).

---

## TL;DR

```toml
# Cargo.toml — bump versions
rr-server = "0.3"
rr-client = "0.3"
rr-core = "0.3"
rr-raft = "0.3"
# … etc.

# New crate (opt-in for Kafka input):
# rr-ingestor-kafka = { version = "0.3", features = ["rdkafka"] }
```

Update one breaking call (see below), recompile, deploy with the [rolling upgrade procedure](upgrading.md). Done.

## Breaking changes

### `ServiceStateMachineAdapter::new` signature

v0.2.x:
```rust
ServiceStateMachineAdapter::new(my_service)
```

v0.3.0:
```rust
ServiceStateMachineAdapter::new(group_id, my_service)
//                              ^^^^^^^^ NEW: required for per-group metric labels
```

The `group_id: u64` is captured at construction so per-group metrics (`rr_snapshot_installs_total{group_id="…"}` etc.) carry the correct label. This was added in Wave 1 alongside F2 security hardening; if your code is fresh from `main` since 2026-04-25 you've already done this.

**Fix in your factory closure**:
```rust
// Before
let factory = Box::new(|_gid| {
    Box::new(ServiceStateMachineAdapter::new(my_service.clone())) as Box<dyn StateMachine>
});

// After
let factory = Box::new(|gid| {
    Box::new(ServiceStateMachineAdapter::new(gid, my_service.clone())) as Box<dyn StateMachine>
});
```

### `DurabilityPolicy` rename

v0.2.x: `DurabilityPolicy::{Strict, Balanced, Fast}`
v0.3.0: `DurabilityPolicy::{Strict, ReplicatedOnly, TestOnly}`

Old names still compile — they're `#[deprecated]` aliases that emit a runtime warning on first use and a compile-time deprecation lint. Plan to migrate before v0.4.

| Old | New | Meaning |
|---|---|---|
| `Strict` | `Strict` | (unchanged) fsync on every commit; the only durable policy |
| `Balanced` | `ReplicatedOnly` | Trust replication for durability; **violates openraft's persistence contract** |
| `Fast` | `TestOnly` | No fsync; **TEST-ONLY**, never production |

The rename surfaces what the `Balanced` and `Fast` modes actually mean. Both are kept for the rare case where an operator runs replicated-only with custom recovery scripts; v0.3+ logs a startup warning explaining the trade.

### `allow_insecure` opt-in

v0.3.0 production binaries refuse to start with raft enabled if TLS + mTLS + admin_token are not all configured. The check is enforced by `validate_security_invariants` at `RrNode::new`.

To run rr without TLS in dev:

```toml
# config.toml
allow_insecure = true
```

Or via CLI:
```bash
rr-server --allow-insecure …
```

Or env var: `RR_ALLOW_INSECURE=true`.

`allow_insecure = true` flips a `rr_security_insecure_mode = 1` gauge so production scrapers can alert on accidental insecure deployments. The dev compose stack and example configs ship with `allow_insecure = true` so they continue to work. Production deployments MUST set this to `false` (the default) and configure TLS + mTLS + admin_token.

See the [TLS deployment guide](tls.md) for the production setup.

## Wire-format changes (snapshot envelope)

### `FramedSnapshot` (Wave 3)

From v0.3.0, `ServiceStateMachineAdapter` wraps your `Service::snapshot()` bytes in a `FramedSnapshot` envelope (8-byte magic prefix `\0rrSNAP1` + bincode body). The envelope carries:

- Your raw `Service::snapshot()` bytes (unchanged).
- Framework state: optional `IdempotencyState` (Wave 4 Tier 2) + optional `IngestorState` (Wave 4 Tier 3).

**Auto-migration on `restore()`**: v0.2.x snapshots that lack the magic prefix are recognized as legacy and decoded as raw user bytes. After the first `snapshot()` call on a v0.3 node the on-disk format is the new envelope. **No operator action needed** — pre-existing clusters continue to read their old snapshots and auto-upgrade in place.

The envelope has a `version: u8` field (current `1`); v0.3 nodes reject `version > 1` rather than guess at an unknown layout. This protects rolling upgrades to future versions from corrupting state.

### `FramedEntry` (Wave 4a, 4d)

Per-Raft-log-entry payloads are similarly wrapped in `FramedEntry { version, offset, idem_key, payload }` when carrying ingestor-sourced entries OR client-side `IdempotencyKey`. Entries without those fields use the bare-bytes path (preserves v0.2 wire format byte-for-byte).

`FramedEntry` also has a `version: u8` field rejected when newer-than-supported.

## Rolling upgrade procedure

v0.3.0 is **mixed-version-safe** for v0.2.x → v0.3.0:

1. **Confirm pre-upgrade health**: leader stable, no replication lag, no chaos-test markers.
2. **Per node**, in any order (one node at a time):
   1. Stop `rr-server` on node.
   2. Replace binary with v0.3.0.
   3. Update `config.toml` if you're adopting any new features (most installs need only the breaking-change fix above).
   4. Start `rr-server`. The node reads its v0.2.x snapshot via the auto-migration path.
   5. Wait for `/ready` to return 200 and `rr_raft_is_leader` to settle (~3 election cycles).
   6. Move to next node.
3. **Verify no `rr_idempotency_*` metrics** appearing on nodes that haven't enabled idempotency — should remain 0.
4. **Verify no `rr_ingestor_*` metrics** appearing on nodes that haven't attached an ingestor.

There is **no required snapshot rebuild step**. Existing snapshots remain valid; the next `snapshot()` will emit the new framed envelope automatically.

## Adopting new features (optional)

### Client-side idempotency

Per-request opt-in. Code that doesn't use it is unchanged.

```rust
let key = IdempotencyKey::new("transfer", request_id_from_app);
let resp = client.send_request_idempotent(group_id, payload, key).await?;
```

See [Idempotency Guide](../guide/idempotency.md).

### Kafka input

Add the `rr-ingestor-kafka` dep and call `attach_ingestor_with_auto_idempotency`:

```toml
[dependencies]
rr-ingestor-kafka = { version = "0.3", features = ["rdkafka"] }
```

```rust
use rr_raft::ingestor_runner::{AutoIdempotency, OffsetMapError};

let ingestor = KafkaIngestor::new(group_id, cfg.clone()).await?;
mgr.attach_ingestor_with_auto_idempotency(
    group_id,
    Box::new(ingestor),
    AutoIdempotency {
        request_type: cfg.topic_for(group_id),
        // `kafka_offset_to_request_id` returns `Result` (fail-closed on
        // undecodable offsets) — map its error into `OffsetMapError`.
        offset_to_request_id: Box::new(|b| {
            kafka_offset_to_request_id(b).map_err(OffsetMapError::new)
        }),
    },
).await?;
```

See [Kafka Input Guide](../guide/kafka-input.md).

## Downgrade procedure

If you need to roll back from v0.3.0 to v0.2.x:

1. **No idempotency or ingestor in use**: rolling downgrade works the same way as the upgrade. v0.3 snapshots that lack `framework_state.idempotency` and `framework_state.ingestor` decode cleanly as raw user bytes on a v0.2 binary, because the user-snapshot trailer is identical.
2. **Idempotency or ingestor was enabled**: a v0.3 snapshot with non-empty `framework_state.*` will fail to decode on v0.2.x (no envelope awareness). To downgrade safely, first **trigger a snapshot** on a v0.3 node where you have manually disabled idempotency/ingestor, OR run a one-shot `Service::restore` on raw v0.2-style bytes via your application's own export path.

The CHANGELOG documents the v0.3 minor versions for which downgrade has been tested in CI.
