## 发现 / Findings

1. **吞吐在 ~34k TPS(128B 写)处饱和**,从 k=100 起曲线变平(32.5k → 34.4k),延迟随并发线性上涨
   (k=500 时 p50 11.6ms = 排队效应)。饱和点与存储无关。
2. **fsync 不是瓶颈**:`strict`(每批 fsync)与 `test_only`(不 fsync)在所有并发档差 <2%(噪声内)。
3. **RocksDB LSM 不是瓶颈**:`mem`(完全去掉 RocksDB)与 rocks/strict 同样差 <2%。
4. **CPU 才是约束**:s2-rocks-strict 期间 rr-server 单进程 CPU 中位 60%(低档并发)、p90 328%、
   峰值 362%(≈3.6 核);三节点高档并发合计接近 11 核机器上限。瓶颈在 CPU 路径
   (gRPC/codec/raft replication/apply 序列化),不在磁盘。
5. S1 串行 161µs p50 = 当前单次提交的 RTT 下限;其中 fsync 占比不显著(对照发现 2)。

## ADR A-0010(WAL)开工判据结论

- **前置条件 1(release 基线):✅ 已满足**(本文档 + raw JSON)。
- **前置条件 2(存储是绑定约束):❌ 不成立。** 数据:strict ≈ test_only ≈ mem(<2%),
  CPU 在饱和点打满。按 `rr-wal-impl.md` 前置条件 2 的原判词:"If CPU saturates before fsync
  queue depth, WAL is premature" —— **WAL 维持 deferred,且 IoBatcher 调优同样无收益**
  (fsync 路径本来就不热)。下一个性能杠杆在 CPU 热路径(prost/bincode 编解码、replication
  序列化、锁竞争),需 profiling 定位后再立项。
