安全模型 / Security Model

安全层包括启动安全门、TLS/mTLS、bearer token、速率限制和审计日志。证书细节见 TLS 指南，事件字段见 审计日志。

The security layer consists of startup gates, TLS/mTLS, bearer tokens, rate limiting, and audit logging. See the TLS guide for certificates and Audit Log for event fields.

启动安全门 G1–G7 / Startup Safety Gates​

RrNode::new 在绑定 socket 前调用 validate_security_invariants。G7 无条件先执行；当 allow_insecure = false 时再聚合 检查 G1–G6，一次列出所有违规。

RrNode::new calls validate_security_invariants before binding sockets. G7 always runs first; with allow_insecure = false, G1–G6 are then aggregated so all violations appear together.

Gate检查内容 / Checkallow_insecure 可绕过 / Bypassable
G1RaftService 未配置 TLS / RaftService without TLS是 / Yes
G2Raft TLS 未要求客户端证书；Raft 没有 bearer-token 通道，mTLS 是唯一对端身份检查 / Raft TLS without mTLS; mTLS is the only Raft peer-identity check是 / Yes
G3配置 bearer token 但未启用 TLS，token 会进入明文 metadata / Bearer tokens without TLS expose them in plaintext metadata是 / Yes
G4AdminService 未启用 TLS / AdminService without TLS是 / Yes
G5AdminService 未配置 admin_token / AdminService without admin_token是 / Yes
G6raft_transport = tcp 没有 TLS、对端认证或限流，必须显式 opt-in / TCP Raft has no TLS, peer authentication, or rate limiting and requires opt-in必须设置 / Required
G7TCP Raft bind 必须解析为 loopback；0.0.0.0、:: 和无法解析的地址均拒绝 / TCP Raft bind must resolve to loopback; wildcard and unparsable addresses fail closed否，始终执行 / No, always enforced

insecure 开关 / The Insecure Override​

仅在本地开发、examples、CI 中使用 --allow-insecure、RR_ALLOW_INSECURE=1 或 [node].allow_insecure = true。启用后启 动日志列出被绕过的门，指标端口暴露 rr_security_insecure_mode = 1；安全模式为 0。生产应对该指标告警。G7 不可绕过。

Use --allow-insecure, RR_ALLOW_INSECURE=1, or [node].allow_insecure = true only for local development, examples, and CI. Startup logs list bypassed gates, and the metrics endpoint exposes rr_security_insecure_mode = 1 (0 in secure mode). Alert on this metric in production. G7 cannot be bypassed.

传输安全与认证 / Transport Security and Authentication​

三个 gRPC 面的认证方式不同：

The three gRPC surfaces deliberately use different authentication models:

服务 / Service加密 / Encryption认证 / Authentication
RaftServiceTLS仅 mTLS；无 bearer-token 路径 / mTLS only; no bearer-token path
ClientServiceTLSclient_token 可选；未设即开放，仅限 dev / Optional client_token; unset means open, dev only
AdminServiceTLS生产必须 admin_token / admin_token required in production

Admin 与 Client 使用独立 token，分别发给运维和应用。token 比较使用常数时间比较。拦截器顺序固定为认证先于限流，因此认证失 败不会消耗业务限流配额；TLS 证书失败更在 gRPC 拦截器之前的握手阶段被拒绝。

Admin and Client use separate tokens for operators and applications. Token comparison is constant-time. Authentication runs before rate limiting, so rejected credentials do not consume application rate-limit quota; certificate failures are rejected even earlier during the TLS handshake.

TOML 的 [auth] 只保存环境变量名，不保存 secret：

The TOML [auth] section stores environment-variable names, never the secrets themselves:

[auth]
admin_token_env = "RR_ADMIN_TOKEN"
client_token_env = "RR_CLIENT_TOKEN"

rr-admin 用 --token-env RR_ADMIN_TOKEN 读取 Admin token，REPL 另用 --client-token-env RR_CLIENT_TOKEN。证书字段和 轮换见 TLS 指南。

rr-admin reads the Admin token through --token-env RR_ADMIN_TOKEN; the REPL uses --client-token-env RR_CLIENT_TOKEN separately. See the TLS guide for certificate fields and rotation.

Cluster Admin Console 的两条边界 / Two Cluster Admin Console Boundaries​

Browser→Console 与 Console BFF→AdminService 是两条独立的 TLS 和认证边界。前者加密浏览器到同源 Console 的 HTTP/JSON/SSE，并用 viewer token 登录；后者加密 BFF 到节点 AdminService 的 gRPC，并使用节点 Admin token。 一条边界已启用 TLS 不代表另一条也已安全。

Browser→Console and Console BFF→AdminService are independent TLS and authentication boundaries. The first protects same-origin Console HTTP/JSON/SSE with HTTPS and viewer-token login; the second protects BFF-to-node AdminService gRPC with TLS and the node Admin token. TLS on one boundary does not secure the other.

连接 / Connection传输 / Transport认证与凭证位置 / Authentication and Credential Location
Browser → Console BFFConsole 自身 HTTPS；非 loopback 必须启用 / Console HTTPS; required for non-loopbackviewer token 只用于登录，换取 15 分钟内存 session；不是节点 Admin token / Viewer token login issues a 15-minute in-memory session; it is not the node Admin token
Console BFF → AdminServicegRPC TLS，按节点要求使用 mTLS / gRPC TLS, with mTLS as required by nodes节点 Admin bearer token 只由 BFF 持有并附加到上游 RPC，不下发浏览器 / The BFF alone holds the node Admin bearer token and attaches it to upstream RPCs; browsers never receive it

session 不持久化，Console 重启会撤销全部 session。cookie 为 HttpOnly、SameSite=Strict，HTTPS 时增加 Secure。 连接 CRUD、candidate/saved test、connect/disconnect、delete 和 POST /api/v1/console/connections/{id}/sources/reconcile 都要求 Origin 与当前 scheme/host 完全一致；启用 viewer 认证时还要求与 session 匹配的 X-Console-CSRF。reconcile 仍只刷新该连接的只读采集，这些检查不增加 任何集群写能力。

Sessions are not persisted, and a Console restart revokes all of them. Cookies are HttpOnly and SameSite=Strict, with Secure under HTTPS. Connection CRUD, candidate/saved tests, connect/disconnect, delete, and POST /api/v1/console/connections/{id}/sources/reconcile require an Origin exactly matching the current scheme/host; with viewer authentication, they also require X-Console-CSRF matching the session. Reconcile remains a read-only refresh for that connection, and these checks add no cluster write capability.

无来源启动不会自动连接节点。每个已连接 runtime 独立持有上游凭证和缓存；浏览器 URL connection ID 不会读取或修改 其他 runtime。非敏感 profile 使用原子 0600 JSON；Admin token、discovery password 默认只在进程内存，显式 Remember 才进入 OS keychain。秘密字段不会出现在 API 响应、URL、浏览器持久存储或 access log。删除 profile 会 断开 runtime 并删除 keychain entry；进程重启后 runtime 不自动恢复。

No-source startup contacts no node. Every connected runtime independently holds upstream credentials and caches, and a browser URL connection ID cannot read or mutate another runtime. Non-sensitive profiles use atomic mode-0600 JSON; Admin tokens and discovery passwords remain in process memory unless Remember explicitly selects the OS keychain. Secret fields never appear in API responses, URLs, browser persistent storage, or access logs. Deleting a profile disconnects its runtime and removes keychain entries; process restart does not restore runtimes automatically.

没有可用 keychain 的隔离/headless 部署可显式传入 --keychain-disable。该进程不会调用 keychain，包括 profile 删除清理；秘密仅保留在内存，UI 禁用 Remember，连接 API 返回 keychain_available=false。默认不传此参数， 生产仍使用 OS keychain。只有内存凭证的 profile 在重启后必须重新输入秘密。

Isolated or headless deployments without a usable keychain can explicitly pass --keychain-disable. The process makes no keychain calls, including delete cleanup; secrets remain memory-only, the UI disables Remember, and the connection API reports keychain_available=false. Omitting the flag preserves OS-keychain use in production. Profiles with memory-only credentials require secret re-entry after restart.

完整启动参数见 TLS 指南， Console 行为见 集群管理控制台。

See the TLS guide for startup flags and the Cluster Admin Console guide for Console behavior.

速率限制 / Rate Limiting​

限流只作用于 AdminService 与 ClientService，RaftService 永不设限。配额耗尽返回 gRPC RESOURCE_EXHAUSTED（code 8）。

Rate limits apply only to AdminService and ClientService, never RaftService. Exhaustion returns gRPC RESOURCE_EXHAUSTED (code 8).

配置 / KnobCLI / Env默认 / Default
admin_rps--admin-rps / RR_ADMIN_RPS不限 / Unlimited
client_rps--client-rps / RR_CLIENT_RPS不限 / Unlimited
burst[rate_limit].burstmax(rps, 10)
per_caller_admin_rps--per-caller-admin-rps / RR_PER_CALLER_ADMIN_RPS关闭 / Disabled
per_caller_client_rps--per-caller-client-rps / RR_PER_CALLER_CLIENT_RPS关闭 / Disabled
per_caller_burst[rate_limit].per_caller_burstmax(per_caller_rps, 10)

设置 per_caller_* 后，已认证调用方按 bearer token 的 siphash 指纹获得独立桶。未认证请求和调用方表已满时的溢出请求使用 对应全局桶，因此必须同时配置 admin_rps 或 client_rps，否则配置校验拒绝启动。空闲超过 300 秒的调用方条目会清理，拒绝 事件写 op="rate_limit", result="rejected" 审计日志。

With per_caller_* set, authenticated callers receive individual buckets keyed by a siphash fingerprint of the bearer token. Unauthenticated requests and callers overflowing the per-caller map use the matching global bucket, so admin_rps or client_rps is also required; validation rejects the configuration otherwise. Caller entries idle for more than 300 seconds are evicted, and rejects emit op="rate_limit", result="rejected" audit events.

审计日志 / Audit Logging​

认证拒绝、限流拒绝和 AdminService RPC 生命周期事件写入专用 tracing target rr::audit。强制成员变更额外写 warn 级 result="force_accepted"，ingestor offset 人工覆盖也写 warn 级事件，DrainNode 按组记录领导权转移。

Authentication rejects, rate-limit rejects, and AdminService RPC lifecycle events use the dedicated tracing target rr::audit. Forced membership changes add a warn-level result="force_accepted" event, manual ingestor-offset overrides are warn-level, and DrainNode records leadership transfers per group.

使用 RUST_LOG="warn,rr::audit=info" 同时保留 warn 拒绝事件和 info RPC 事件。schema、sink 和限制见 审计日志指南。

Use RUST_LOG="warn,rr::audit=info" to retain both warn-level rejects and info-level RPC events. See the audit-log guide for schema, sinks, and limitations.

成员变更护栏 / Membership Safety Guard​

MIN_VOTERS_AFTER_REMOVAL = 2 由服务端和 rr-admin node decommission 预检共享。openraft joint consensus 保证成员变更的 一致性，但不保证变更后的可用性；该护栏阻止常规操作缩成单点。

MIN_VOTERS_AFTER_REMOVAL = 2 is shared by the server and the rr-admin node decommission precheck. Openraft joint consensus keeps membership changes consistent but does not guarantee availability afterward; this guard prevents routine changes from creating a single point of failure.

变更 / Change无 force / No Force有 force / With Force
3→2允许 / Allowed允许 / Allowed
3→1 / 2→1failed_precondition允许并写 warn 审计 / Allowed with warn audit
1→1 换 voter / voter swap拒绝 / Rejected允许并写 warn 审计 / Allowed with warn audit
n→0invalid_argument仍拒绝；不能绕过 / Still rejected; not bypassable
2→3 等扩容 / growth允许 / Allowed允许 / Allowed

只有运行新二进制的 server 才执行新护栏。滚动升级期间不要依赖它：旧 server 的 proto3 解码会忽略未知 force 字段。不要把 --force 当作常规缩容工具。

Only servers running the new binary enforce the new guard. Do not rely on it during a rolling upgrade: an old server's proto3 decoding ignores the unknown force field. Never use --force for routine shrink operations.

实验性 TCP Raft / Experimental TCP Raft Transport​

RaftTransport::Tcp（--raft-transport tcp）只承载 AppendEntries/Vote，InstallSnapshot 始终回退 gRPC，因此 gRPC TLS/mTLS 门仍适用。TCP frame 协议没有 TLS、对端认证或限流，任何能到达端口的人都可注入帧。

RaftTransport::Tcp (--raft-transport tcp) carries only AppendEntries/Vote; InstallSnapshot always falls back to gRPC , so gRPC TLS/mTLS gates still apply. The TCP frame protocol has no TLS, peer authentication, or rate limiting; anyone who can reach the port can inject frames.

因此必须显式 --allow-insecure，且 bind 只能为 loopback。TCP 端口默认从 gRPC 端口 +10000 派生，可用 --raft-tcp-port / RR_RAFT_TCP_PORT 覆盖。库用户直接调用 TcpRaftServer::bind 会绕过这些启动门，不要绑定非 loopback。生产使用默认 gRPC

transport。

It therefore requires explicit --allow-insecure and a loopback bind. The TCP port defaults to gRPC port +10000 and can be overridden with --raft-tcp-port / RR_RAFT_TCP_PORT. Library users calling TcpRaftServer::bind directly bypass the startup gates; never bind it off-loopback. Use the default gRPC transport in production.

本地开发 / Insecure Local Development​

本地可使用明文 + --allow-insecure，或生成开发证书演练真实 TLS：

For local work, use either plaintext + --allow-insecure or generate development certificates to rehearse real TLS:

./scripts/gen-dev-certs.sh dev-certs 3

脚本生成自签名开发 CA（RSA-4096，10 年）和每节点 cert/key（RSA-2048，1 年），SAN 覆盖 localhost、127.0.0.1、::1、 rr-N、nodeN.rr.local，key 权限为 600。

The script creates a self-signed development CA (RSA-4096, ten years) and per-node cert/key pairs (RSA-2048, one year), with SANs for localhost, 127.0.0.1, ::1, rr-N, and nodeN.rr.local; keys use mode 600.

这些证书不得用于生产。 私钥不加密，SAN 只覆盖本地主机名。完整启动命令见 TLS 指南。

Never use these certificates in production. Private keys are unencrypted and SANs cover local hostnames only. See the TLS guide for full launch commands.
